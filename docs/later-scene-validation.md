# Middle- and late-story scene-entry validation

Date: 2026-11-27. Local experiment on `scene-entry-prototype`; no editor or public
deployment changes. This extends [the initial scene-2 proof](scene-preview-feasibility.md).

## Result and scope

**Four additional scenes pass with an explicitly prepared mission-entry context.**
Each has an original baseline, edit A adding dialogue, and edit B adding a native
flag conditional and different dialogue. The original VM executes the compiled
program, loads the expected map, creates the expected cast, and reaches the
edited dialogue. Actor positions, facing, visibility and initial camera match
the baseline. All frames are generated by the native WASM core.

This validates selected scene entries and their initial cutscene sequence, not
whole-scene endings, battle outcomes, rewards, arbitrary story progression,
all branch combinations, or browser integration. The observed flag branch in
edit B is the false path on this fixture. It is not a both-outcomes claim.

| Scene | Story context | Native map ID | Actors / visible | Frames to original or added dialogue, baseline / A / B |
| --- | --- | --- | --- | --- |
| 53 | Mid-story, after three crystals; pub conversation | 63 | 7 / 7 | 132 / 132 / 132 |
| 93 | Late-story palace arrival | 37 | 9 / 3 | 1,129 / 1,129 / 1,129 |
| 98 | Final confrontation | 38 | 8 / 3 | 130 / 130 / 130 |
| 101 | Ending transition | 101 | 2 / 2 | 308 / 308 / 308 |

Scene selection is based on the original script and its story content, not
merely choosing large scene IDs. Map IDs here are the game's one-based IDs.
Native introductory waits, actions and camera timing are executed, not skipped.
The report also records the host time: roughly 0.4–1.7 seconds per run including
120 settling frames on this Node/WASM host. These are not browser latency figures.

## Why the first reused context failed

Borrowing the earlier post-Snowball checkpoint was **not valid for these scenes**.
The map and VM could change while actor initialization failed. Runs reached an
undefined-instruction exception or an invalid ARM PC before the new dialogue.
Merely counting emulated frames or displaying a map would have hidden the failure.

Controls performed locally:

- An unmodified original ROM also fails under that borrowed context. The problem
  is not established to be caused by the new text or script allocation.
- Native mGBA 0.10.5 reproduces the scene-53 failure with the same candidate and
  borrowed checkpoint: ARM PC `0x00000008`, CPSR `0x9b`. It is not a WASM-only result.
- Setting event flag 1 or substituting a late-game party roster does not repair
  the borrowed context. Those changes are not a sufficient initialization contract.
- Loading the later save normally reaches the world map, but writing a queue
  request there does not activate the required scene lifecycle by itself.

These controls narrow the failure to the entry/runtime context; they do not yet
identify the minimal set of missing initialization steps. No VM wait was forced
complete, no actor action was skipped, and no faulted run is counted as passing.
Failed trial artifacts remain local outside Git.

## Successful context preparation

The original ROM boots with a local late-game SAV and follows recorded native
menu input into a mission. The save-selection screen showed approximately
60 hours and 300 completed missions. The one-time preparation stops at frame
**2,489**, when scene 14 becomes pending and its VM has not been allocated.
Preparation uses **no manual game-memory writes**.

The checked boundary is:

```text
scene = 14
VM root = 0
script active = 0
outer scene system = 9
queue count = 1, queue head = 14
content = 32
```

This differs from the school checkpoint, where the outer scene system was 0.
It includes the game's real save loading, party/progress state, mission selection
and outer transition initialization. It is a usable fixture for these four tests;
it is not proof that changing the system byte alone would fix another checkpoint.

For scenes 53, 98 and 101, the harness changes the pending and current selector
halfwords at `0x02002194` and `0x02002192` **before** VM allocation. These two
explicit test-entry writes select the target; they do not skip its instructions.
The original lifecycle then creates and executes the target task. There are no
manual game-memory writes during the scene itself.

Scene 93 additionally depends on its caller's encounter selection. Its test-only
scene-14 bootstrap executes three **existing native instructions**:

```text
selectSceneEncounter(93)
queueScene(93)
setSceneRuntimeMode(1)
```

This selects encounter definition 26 / content 58 before the palace script loads
map 0 from that context. There are no host RAM writes for this route, custom
opcodes, CPU-call trampolines, or new ARM patches. The bootstrap is part of the
local test project, not a change shipped to users.

These are synthetic preview entries seeded by genuine gameplay context. They do
not establish natural reachability of these story events from the chosen save.

## False-positive control

Without the encounter bootstrap, scene 93 **still executes the newly added
dialogue**, but loads map **71**, the inherited mission field, instead of palace
map **37**. Its task and PC checks pass while its map contract fails.
The verification deliberately reproduces and rejects this case.

Therefore “new text appeared” and “scene ID matches” are both insufficient
acceptance conditions. A valid scene-entry fixture must also declare and verify
the map, cast, relevant context and expected branch behavior.

## Reproduce

[tools/probe-later-scenes.mjs](../tools/probe-later-scenes.mjs) keeps all game
inputs and output outside Git. Input records can be JSON `{frames, keys}` rows,
or two-column text with decimal frames and hexadecimal GBA key masks.

```sh
node tools/probe-later-scenes.mjs prepare /path/to/retail.gba \
  /outside/progress.sav /outside/native-keys.input /outside/checkpoint
node tools/probe-later-scenes.mjs verify /path/to/retail.gba \
  /outside/checkpoint /outside/results
```

Assertions check input/core/checkpoint hashes, pre-load state, task ownership,
script base and PC, map, actor identity/position/facing/visibility, initial camera,
native condition polarity, distinct revisions, and fault-free CPU execution.
The actor registry is read using the original list/lookup layout; it is not an
invented JS cast. A CPU exception is failure even if video frames keep advancing.

Local evidence root: `/tmp/ffta-composer-wasm/later-proof/`.
`results/report.json` contains the 12 positive runs and wrong-map control;
PNG files show the original native framebuffer. The independent repeat is under
`recheck/`. All 12 runs reproduced identical candidate/script/framebuffer hashes,
VM traces, actor state, camera and entry timing. The wrong-map control was rejected
again. The repeat report also pins the probe source SHA-256. ROM/project pairs,
native states and SAVs remain local.
